# 执行器参考

执行器是 ExecGo 真正把任务落到现实世界的那一层。你可以把 `Task` 理解成“执行请求”，把执行器理解成“执行这条请求的具体能力实现”。

## 先记住一个核心心智模型

当前最实用的理解方式是：

- `type` 决定走哪一类执行器
- `tool_name` 决定在这一类执行器里具体调用哪个工具
- `params` 或 `input` 提供实际输入

如果你使用的是便捷写法，例如 `type: "shell"`、`type: "file"`，服务端通常会先把它规范化成统一类别再执行。

## 主线里最常见的内置能力

### `os` 类别

这是最常用的一组内置工具，通常包括：

- `shell`
- `file`
- `dns`
- `tcp`
- `sleep`
- `noop`
- `http`

### 其他类别

- `mcp`：接入 MCP 工具调用
- `cli-skills`：接入本地 CLI + Skills 能力

## 第一次接入时最常用的三个工具

### shell

适合执行受控命令。最需要注意的是安全边界，不要把它当成完全不受约束的远程命令执行入口。

### file

适合做本地文件读写、追加、删除、查询元信息。使用时要特别留意工作目录、路径规范化和越权访问风险。

### http

适合访问外部 HTTP 服务。它通常是最容易和上层工作流打通的执行器，但也要留意超时、重试和外部依赖的不稳定性。

## 便捷写法和统一写法有什么区别

第一次接入时，你很可能更愿意这样写：

```json
{
  "id": "say-hello",
  "type": "shell",
  "params": {
    "command": "echo hello"
  }
}
```

而运行时内部更接近下面这种结构：

```json
{
  "id": "say-hello",
  "type": "os",
  "tool_name": "shell",
  "input": {
    "command": "echo hello"
  }
}
```

两者最终会落到同一条执行路径上。前者更适合人读，后者更适合统一模型。

## 什么时候需要读更细的执行器文档

当你遇到下面这些问题时，就该深入拆分页了：

- 某个工具到底支持哪些参数
- shell 是否有限制
- file 是否有路径边界保护
- 我想扩展自定义执行器该从哪里下手
