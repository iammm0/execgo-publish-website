# 轮询与幂等

ExecGo 的 `POST /tasks` 是异步接口。它返回 `202 Accepted` 时，只表示“任务图已经被服务接收”，不表示任务已经执行完成。真正把接入做稳，关键在后半段：怎么轮询、什么时候停、怎么避免重复提交。

## 先记住三个原则

1. 提交成功不等于执行成功。
2. `task.id` 更像一次执行记录的主键，而不是一个随便起的展示名称。
3. `DELETE /tasks/{id}` 只删除状态记录，不等价于取消正在运行的任务。

## 一个推荐的交互闭环

最常见也最稳妥的调用流程是：

1. 调用 `POST /tasks`
2. 记录返回的 `task_ids`
3. 对每个任务调用 `GET /tasks/{id}` 轮询状态
4. 当状态进入 `success`、`failed` 或 `skipped` 时停止轮询
5. 成功时读取 `result`，失败时读取 `error`

如果你的编排是分阶段提交，那么每一阶段都应该重复这个流程，而不是假设“提交下一阶段时上一阶段一定已经结束”。

## 为什么 task.id 会直接影响幂等

默认状态存储会用 `task.id` 作为索引键。于是就会出现一个非常实际的问题：

- 如果你因为网络抖动、超时或客户端重试，再次提交了一组相同的 `task.id`
- 服务端很可能会把旧记录覆盖成新的任务状态

所以，幂等策略本质上就是你如何管理 `task.id`。

## 两种常见策略

### 策略 A：同一次工作流运行复用 task.id

适合“重复请求不应触发重新执行”的场景。

推荐做法：

1. 为一次 workflow run 生成稳定的任务 ID
2. 如果提交结果不确定，先用 `GET /tasks/{id}` 查是否已经存在
3. 已存在且状态是终态，就直接读取结果
4. 已存在但仍在 `pending` 或 `running`，继续轮询，不要再提交

### 策略 B：每次重跑都生成新的 task.id

适合“允许重复执行，但要区分不同轮次”的场景。

常见做法是把这些信息拼进 ID：

- 业务主键
- workflow run ID
- attempt 序号

这样你能明确区分“同一次运行的重试”和“新的业务执行轮次”。

## 一个简单可靠的轮询建议

可以用指数退避来避免把查询频率打得太高：

- 初始间隔：`500ms`
- 每轮乘以 `1.5` 到 `2`
- 最大间隔：`5s`

如果任务通常很短，这个策略已经足够；如果任务特别长，你可以把最大间隔再拉高。

## 哪些状态可以停止轮询

下面这三个状态都可以视为终态：

- `success`
- `failed`
- `skipped`

然后再按语义区分：

- `success`：读取 `result`
- `failed`：读取 `error`
- `skipped`：去上游依赖链找根因

## DELETE 为什么不能当取消接口

`DELETE /tasks/{id}` 删除的是状态存储里的那条记录。它不是一个强语义的“取消运行”接口，所以你不应该基于它设计“任务中断”流程。

更安全的理解方式是：

- 它适合做清理和回收
- 不适合拿来保证执行中断

## 当下游参数依赖上游结果时怎么办

这时最稳妥的方式通常是分阶段提交：

1. 先提交上游任务
2. 轮询拿到 `result`
3. 在编排层把结果注入下一张 `TaskGraph`
4. 再提交下游任务

这种方式虽然显式，但行为稳定，也最容易排错。
