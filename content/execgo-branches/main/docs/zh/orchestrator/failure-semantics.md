# 失败与跳过语义

把 ExecGo 接到自己的工作流里以后，最容易被误读的不是接口字段，而是状态含义。尤其是 `failed` 和 `skipped`，如果理解错了，后面的重试、告警和人工介入都会跟着出问题。

## 先看最重要的结论

- `failed` 表示这条任务自己真的执行过，但最终没有成功。
- `skipped` 表示这条任务根本没有执行，通常是因为上游依赖失败了。
- `retry` 只影响当前任务自己的尝试次数，不会改变整张依赖图的传播规则。

## ExecGo 如何处理一次失败

一个任务从提交到结束，大致会经历下面的判断链：

1. 任务进入 `pending`
2. 依赖满足后进入 `running`
3. 执行成功则变成 `success`
4. 执行失败时，如果还有重试额度，就继续尝试
5. 所有尝试都失败后，状态才最终落到 `failed`

换句话说，`failed` 是“重试已经用完之后的最终结论”，不是某一次瞬时失败。

## retry 和 timeout 应该怎么理解

### retry

- `task.retry = 0` 表示只执行 1 次
- `task.retry = 2` 表示最多执行 3 次

`retry` 写的是“额外重试次数”，不是总尝试次数。

### timeout

- `task.timeout` 作用于单次执行
- 如果任务进入重试，下一次尝试会重新开始计时

所以它更像“每一轮执行的时间上限”，而不是整条任务从提交到结束的总耗时上限。

## 为什么下游会变成 skipped

当一个任务最终 `failed`，所有直接依赖它的下游任务都会因为前置条件不满足而被标记为 `skipped`。这件事还会继续向更深层级联传播。

这意味着：

- 失败根因通常出现在最上游的 `failed` 节点
- 被动跳过的节点不应该被当成新的失败根因
- 你的告警和诊断逻辑应该优先定位第一个真正失败的任务

## 编排层应该如何解读这些状态

### 看到 success

- 可以继续推进后续逻辑
- 如果下游参数依赖结果，记得从 `result` 或 `runtime.output` 里取值并自行注入

### 看到 failed

- 说明这条任务已经执行过，而且重试也没救回来
- 你应该读取 `error` 或 `runtime.error`，决定是告警、补偿还是人工介入

### 看到 skipped

- 先不要在这条任务上继续纠缠
- 回头找到它依赖链上第一个 `failed` 的任务
- 你的 UI 和日志里，最好把它标成“上游失败导致未执行”，而不是“本任务执行失败”

## 一个很实用的处理建议

在轮询或消费状态时，可以把终态分成两类：

- 可继续推进：`success`
- 需要停止或改道：`failed`、`skipped`

然后再在第二层判断里区分：

- `failed` 需要看本任务错误详情
- `skipped` 需要回溯上游失败根因

这样的处理方式通常最贴近真实的业务决策流程。
