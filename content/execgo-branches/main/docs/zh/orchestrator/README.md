# 编排接入指南

如果你准备把 ExecGo 放在上层 Agent、工作流引擎或业务编排层的下方，这一组文档应该先读。它们不讨论某个执行器的细枝末节，而是先帮助你建立三个最关键的判断：

1. 你的工作流应该如何翻译成 ExecGo 能接受的 `TaskGraph`
2. 任务失败以后，应该如何理解 `failed` 和 `skipped`
3. 异步执行场景下，怎样做稳定的轮询和幂等控制

## 先建立一个简单心智模型

ExecGo 的职责很克制：它负责接收一张任务图，按依赖关系调度执行，并把结果回写到每个任务上。它不会替你做这些事：

- 不会自动把上游结果注入下游参数
- 不会替你决定业务层面的补偿或分支逻辑
- 不会把“是否重新提交”这种幂等策略替你封装好

换句话说，上层编排层负责“什么时候提交什么任务图”，ExecGo 负责“把这张图按约定执行出来”。

## 推荐阅读顺序

### 1. 先看映射关系

[DAG 到 TaskGraph 的映射](./mapping-dag-to-taskgraph.md)

这篇会解释节点、边、参数、依赖、超时和重试如何落到 `Task` 字段上。第一次接入时，大部分误解都发生在这里。

### 2. 再看失败语义

[失败与跳过语义](./failure-semantics.md)

很多接入方会把 `failed` 和 `skipped` 混为一谈，结果在告警、重试和人工介入时做出错误判断。这篇会把状态语义掰开讲清楚。

### 3. 最后看轮询与幂等

[轮询与幂等](./polling-and-idempotency.md)

`POST /tasks` 返回 `202 Accepted` 以后，真正的工作才刚开始。你需要决定怎么查状态、何时停止轮询、如何避免重复提交同一个 `task.id`。

## 什么时候应该拆成多次提交

只要下游任务的参数需要依赖上游运行结果，就不建议强行把整条链一次性塞进同一张 DAG。更稳妥的做法通常是：

1. 先提交上游任务
2. 轮询拿到 `result` 或 `error`
3. 由你的编排层把结果注入下一张 `TaskGraph`
4. 再提交下游任务

这种方式虽然少了一点“魔法感”，但行为更可预测，也更利于排错。
