# 执行器参考

即使 `feat-add-cluster` 分支已经开始把运行时做得更厚，执行器依然是任务真正落地执行的那一层。对外阅读时，最值得先掌握的仍然是统一模型，而不是某个具体实现细节。

## 先记住一个核心心智模型

- `type` 决定走哪一类执行器
- `tool_name` 决定具体调用哪个工具
- `params` 或 `input` 提供输入

便捷别名写法依然可用，但统一类别写法会更接近这条分支未来的运行时形态。

## 最常见的内置能力

### `os` 类别

通常包括：

- `shell`
- `file`
- `dns`
- `tcp`
- `sleep`
- `noop`
- `http`

### 其他类别

- `mcp`
- `cli-skills`

随着这条分支继续演进，执行器本身会越来越像“统一运行时能力的入口”，而不只是几个松散的工具封装。

## 第一次接入时最常用的三个工具

### shell

最灵活，也最需要谨慎。真正进入生产环境前，一定要先考虑命令白名单、工作目录、网络权限和超时边界。

### file

适合做文件读写，但要尤其留意路径边界和越权访问。

### http

最适合对接外部服务，也是最容易和 Agent 编排配合的工具之一。

## 便捷写法和统一写法

### 便捷写法

```json
{
  "id": "say-hello",
  "type": "shell",
  "params": {
    "command": "echo hello"
  }
}
```

### 更统一的写法

```json
{
  "id": "say-hello",
  "type": "os",
  "tool_name": "shell",
  "input": {
    "command": "echo hello"
  }
}
```

如果你后续要更深入利用运行时语义、句柄和审计能力，统一写法通常更容易和未来模型对齐。

## 什么时候需要继续往下看

当你遇到下面这些问题时，就应该深入拆分页：

- 某个工具支持哪些参数
- 如何给危险执行器加策略限制
- 如何扩展自定义执行器
- 未来的运行时钩子和执行生命周期如何统一
