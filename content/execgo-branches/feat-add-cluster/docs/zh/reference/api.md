# API 参考

`feat-add-cluster` 分支对外仍然保留熟悉的 HTTP 提交与查询模式，所以第一次接入时，你仍然可以按稳定版的思路来理解这组 API。这篇的重点，是先把最常用的调用顺序和字段用途讲清楚。

## 最常用的接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/tasks` | 提交一张任务图 |
| `GET` | `/tasks/{id}` | 查询单个任务状态与结果 |
| `GET` | `/tasks` | 列出当前任务 |
| `DELETE` | `/tasks/{id}` | 删除任务状态记录 |
| `GET` | `/health` | 健康检查 |
| `GET` | `/metrics` | 读取 JSON 指标 |

如果你进一步接入更丰富的控制面能力，还需要结合这条分支的 gRPC 和运行时设计资料一起看，但第一次接入通常先不用把范围拉那么大。

## 一次典型调用会怎么走

1. `POST /tasks` 提交任务图
2. 保存返回的 `task_ids`
3. `GET /tasks/{id}` 轮询状态
4. 终态后读取结果或错误
5. 需要时再 `DELETE /tasks/{id}` 清理记录

这条分支内部可以更复杂，但外部这套交互流程不应该被搞得更难懂。

## POST /tasks 最值得注意什么

### `202 Accepted` 的含义

表示“接收成功，后台开始推进”，不表示“已经执行完成”。

### 最容易触发 `400` 的原因

- `task.id` 重复
- `depends_on` 引用了不存在的任务
- 图里有环
- `type` 或参数结构不合法

所以 `Task DSL` 依然是第一次排错时最该一起打开的文档。

## GET /tasks/{id} 应该优先看哪些字段

先看：

- `status`
- `result`
- `error`

如果你想利用这条分支更丰富的运行时信息，再继续看：

- `runtime.output`
- `runtime.error`
- 未来的句柄和结构化错误字段

推荐的读取顺序仍然是：

1. 先判断 `status`
2. 成功时读结果
3. 失败时读错误
4. `skipped` 时回溯上游失败点

## DELETE /tasks/{id} 适合做什么

仍然更适合拿来清理状态，而不是做强语义取消。随着运行时逐步变厚，真正的取消能力更可能作为独立语义出现，而不是继续借用 `DELETE`。

## /health 和 /metrics 的角色

- `/health`：可用性确认、启动探针、运行状态判断
- `/metrics`：基础指标采集和监控接入
