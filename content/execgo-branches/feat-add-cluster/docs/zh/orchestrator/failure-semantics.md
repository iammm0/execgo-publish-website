# 失败与跳过语义

`feat-add-cluster` 分支内部已经开始把执行过程拆成更明确的运行时层，但对上层编排逻辑来说，最先要看懂的仍然是任务终态。尤其是 `failed` 和 `skipped`，如果在这里判断错了，后续的回退、重试和告警都会跟着跑偏。

## 先看最重要的结论

- `failed` 表示这条任务真正执行过，但最终没有成功。
- `skipped` 表示这条任务没有执行，通常是因为上游失败导致没有资格进入执行阶段。
- `retry` 只作用于当前任务自己的尝试次数，不改变依赖传播规则。

## ExecGo 如何处理一次失败

1. 任务先进入 `pending`
2. 依赖满足后进入 `running`
3. 执行失败时，如果还有重试额度，就继续尝试
4. 所有尝试都失败后，任务才会真正落到 `failed`
5. 依赖这条任务的下游，则会继续被标记成 `skipped`

即使这条分支以后会暴露更细的 `runtime.status`，调度层面对 `failed` 和 `skipped` 的判断逻辑依然应该保持稳定。

## retry 和 timeout 的正确理解

### retry

- `retry = 0` 表示只尝试 1 次
- `retry = 2` 表示最多尝试 3 次

### timeout

- `timeout` 作用于单次执行
- 如果任务进入下一轮重试，会重新计算超时窗口

也就是说，`timeout` 更像“单轮执行预算”，而不是这条任务从提交到结束的总预算。

## 为什么下游会被 skipped

当一个任务最终 `failed`，依赖它的任务就不再满足执行前提。ExecGo 会把这些任务标成 `skipped`，而不是再把它们也当作新的失败去执行一遍。

这背后的意义是：

- 真正的根因通常在最早的 `failed` 节点上
- `skipped` 是编排传播结果，不是新的执行故障
- 你的诊断逻辑应该优先找到第一个失败点，而不是在被跳过的节点上做重复分析

## 在这条分支里该看哪些错误字段

如果你只是做兼容接入，可以继续看：

- `status`
- `result`
- `error`

如果你还想进一步利用预览中的运行时语义，可以继续看：

- `runtime.output`
- `runtime.error`
- 未来更明确的结构化错误字段

但不管你取哪一层字段，`failed` 和 `skipped` 的业务判断都不应该混在一起。

## 编排层的一个实用判断方式

你可以先把终态分成两类：

- 可继续推进：`success`
- 需要停下来处理：`failed`、`skipped`

然后再细分：

- `failed`：读取本任务错误详情，决定是否重试、补偿或告警
- `skipped`：回到上游依赖链，寻找真正失败的节点
