# 轮询与幂等

无论内部运行时是否已经演进到事件溯源、队列和 Worker，`feat-add-cluster` 分支对上层的基础交互仍然是异步的：`POST /tasks` 返回 `202 Accepted`，只代表接收成功，不代表执行已经完成。真正决定接入稳定性的，是后续的查询和去重策略。

## 先记住三个原则

1. 接收成功不等于执行成功。
2. `task.id` 依然是你设计幂等策略时最关键的锚点。
3. 删除状态记录不等于取消运行中的任务。

## 一个推荐的调用闭环

1. 调用 `POST /tasks`
2. 保存返回的 `task_ids`
3. 轮询 `GET /tasks/{id}`
4. 状态进入终态以后停止轮询
5. 成功时读取 `result` 或 `runtime.output`，失败时读取 `error` 或 `runtime.error`

如果你采用分阶段提交，就把这一套流程当成每一阶段都要执行的固定动作。

## 为什么 task.id 会直接影响幂等

默认情况下，服务端仍然会把 `task.id` 当成任务记录的核心索引。如果你在客户端因为超时或重试又提交了一次同名任务，就可能出现：

- 旧记录被覆盖
- 任务被重新推进
- 查询结果和你预期的不一致

所以幂等问题，本质上还是 ID 管理问题。

## 两种常见策略

### 策略 A：同一次运行复用 task.id

适合“重复请求不应该重新执行”的场景。

推荐做法：

1. 为一次 workflow run 生成稳定 ID
2. 如果提交结果不确定，先查 `GET /tasks/{id}`
3. 已存在就不要盲目重新提交
4. 已结束则直接消费结果，未结束则继续轮询

### 策略 B：每次真正重跑都生成新 ID

适合“允许重复执行，但要区分运行轮次”的场景。通常会把业务主键、run ID 和 attempt 信息组合进任务 ID。

## 轮询频率建议

推荐使用指数退避：

- 初始间隔：`500ms`
- 每轮乘以 `1.5` 到 `2`
- 最大间隔：`5s`

如果未来这条分支暴露更丰富的句柄或事件订阅能力，你可以再逐步升级成“轮询 + 订阅”的混合模式；但在当前阶段，稳妥的指数退避已经足够实用。

## 哪些状态可以停止轮询

仍然以这三个终态为准：

- `success`
- `failed`
- `skipped`

然后再按你的接入层次读取字段：

- 只做兼容接入：看 `result` / `error`
- 想消费更明确的运行时包络：看 `runtime.output` / `runtime.error`

## DELETE 为什么不能当取消接口

当前更可靠的理解仍然是：

- `DELETE /tasks/{id}` 负责清理状态
- 它不负责保证运行一定被中止

因此不要把业务层面的“取消任务”语义建立在这个接口上。

## 当下游参数依赖上游结果时怎么办

判断标准和稳定线一致：这通常意味着你应该拆成多次提交。

1. 先提交上游任务
2. 轮询拿到结果
3. 在编排层根据结果决定下一步
4. 再提交下一张 `TaskGraph`

内部是不是队列化调度，不会改变这条建议。
